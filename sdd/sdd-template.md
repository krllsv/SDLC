## 1. Введение
### 1.1 Назначение документа
Настоящий SDD описывает архитектуру и дизайн веб-приложения платформы для поиска репетиторов на основе утвержденного документа SRS версии 0.1. Документ предназначен для команды разработчиков (Frontend и Backend), тестировщиков и архитекторов для понимания того, как система будет реализована технически.

### 1.2 Область применения
Проектируемая система — веб-приложение платформы «TutorPlatform». Включает клиентскую часть (SPA) для учеников и репетиторов, административную панель для модераторов и серверную логику для обработки заявок. Система не включает модуль онлайн-оплаты и собственную видеоплатформу (согласно границам проекта в SRS). 

### 1.3 Определения, акронимы и сокращения
| Term | Definition |
|------|------------|
| API | Application Programming Interface — программный интерфейс взаимодействия |
| SDD | Software Design Document — документ описания дизайна ПО |
| SPA | Single Page Application — одностраничное веб-приложение |
| JWT | JSON Web Token — стандарт аутентификации |
| ORM | Object-Relational Mapping — технология связывания БД и кода |

### 1.4 Ссылки

### 1.5 Обзор документа
Документ состоит из 5 разделов. Раздел 2 описывает задачи стейкхолдеров и выбранные точки зрения. Раздел 3 содержит проектные представления. Раздел 4 фиксирует архитектурные решения (ADR) и план итераций. Раздел 5 включает приложения.

## 2. Обзор дизайна
### 2.1 Задачи стейкхолдеров
- **Заказчик:** заинтересован в быстрой работе поиска (отклик < 500 мс), надежном сохранении бронирований и защите персональных данных пользователей.
- **Frontend-разработчики:** нуждаются в четком описании контрактов REST API для интеграции React с сервером.
- **Backend-разработчики:** нуждаются в понимании структуры базы данных (связи репетиторов, учеников и бронирований) и логики фильтрации.
- **QA-инженеры:** нуждаются в понимании статусной модели бронирования для написания тест-кейсов.

### 2.2 Выбранные точки зрения
Для описания системы выбраны ключевые точки зрения. Для каждой точки зрения определен свой язык моделирования.

**2.2.1 Контекст**
Адресует: границы системы, акторы окружения и предоставляемые сервисы. Применение в проекте: Описание взаимодействия с Учеником, Репетитором, Администратором, API карт (Leaflet) и SMTP-сервером. Язык: Контекстная диаграмма (C4).

**2.2.2 Композиция**
Адресует: выявление основных элементов дизайна и интеграцию. Применение в проекте: Описание клиент-серверной архитектуры (React SPA, Node.js + Express, PostgreSQL). Язык: Диаграмма компонентов.

**2.2.3 Логическое представление**
Адресует: статическую структуру дизайна с точки зрения типов и их взаимосвязей. Применение в проекте: Описание объектной модели данных (сущности ORM) и их связей. Язык: Диаграмма классов.

**2.2.7 Информация**
Адресует: структуру постоянных данных. Применение в проекте: Описание реляционной схемы базы данных PostgreSQL. Язык: ER-диаграмма (сущность-связь).

**2.2.8 Интерфейс**
Адресует: внешние видимые интерфейсы между компонентами. Применение в проекте: Спецификация REST API для обмена данными между React и Node.js. Язык: Спецификация OpenAPI (Swagger).

**2.2.11 Динамика состояний**
Адресует: эволюцию состояний системы в ответ на события. Применение в проекте: Описание жизненного цикла заявки на бронирование. Язык: Диаграмма состояний.

**2.2.14 Развёртывание**
Адресует: отображение программных сущностей на физическое окружение. Применение в проекте: Описание развертывания Docker-контейнеров на сервере. Язык: Диаграмма развёртывания.

## 3. Проектные представления

**ID: 001-context**
- **Title:** Контекст системы
- **Viewpoint:** Контекст
- **Representation:** Система выступает центральным компонентом. Акторы: Ученик (браузер), Репетитор (браузер), Администратор. Внешние системы: OpenStreetMap API (геолокация), SMTP-сервер (email-уведомления).
- **More Information:** Реализует требования раздела 3.1.3 SRS.

**ID: 002-composition**
- **Title:** Композиция и архитектура
- **Viewpoint:** Композиция
- **Representation:** Клиент-серверная архитектура. Состоит из 3 уровней: Frontend (React SPA), Backend (Node.js + Express с REST-контроллерами), Database (PostgreSQL).
- **More Information:** Реализует требования REQ-FUNC-001, REQ-FUNC-004, REQ-FUNC-007.

**ID: 003-structure**
- **Title:** Слоевая структура Backend
- **Viewpoint:** Структура
- **Representation:** Backend разделен на слои: Контроллеры (принимают HTTP-запросы), Сервисы (бизнес-логика, например, фильтрация), Репозитории (взаимодействие с БД).
- **More Information:** Обеспечивает слабую связность и тестируемость кода.

**ID: 004-information**
- **Title:** Модель данных
- **Viewpoint:** Информация
- **Representation:** Реляционная база данных. Основные таблицы:
  - `Users` (id, email, password_hash, role)
  - `TutorProfiles` (user_id, subject, price, format, location)
  - `Bookings` (id, tutor_id, student_id, date, status)
  - `Reviews` (id, tutor_id, rating, comment)
- **More Information:** Реализует требования REQ-FUNC-003, REQ-FUNC-006, REQ-FUNC-007.

**ID: 005-interface**
- **Title:** REST API Контракты
- **Viewpoint:** Интерфейс
- **Representation:** Обмен JSON-сообщениями по HTTP.
  - `GET /api/tutors` — поиск репетиторов (REQ-FUNC-004).
  - `POST /api/bookings` — создание брони (REQ-FUNC-007).
  - `POST /api/reviews` — добавление отзыва (REQ-FUNC-006).
- **More Information:** Отражает нефункциональное требование 3.3.1 (отклик API < 1 сек).

**ID: 006-state-dynamics**
- **Title:** Жизненный цикл бронирования
- **Viewpoint:** Динамика состояний
- **Representation:** Статусы брони: `Pending` (Ожидает) -> `Confirmed` (Подтверждено репетитором) -> `Completed` (Завершено) или `Cancelled` (Отменено). Переход между статусами осуществляется участниками.
- **More Information:** Реализует требование REQ-FUNC-007.

**ID: 007-deployment**
- **Title:** Развёртывание системы
- **Viewpoint:** Развёртывание
- **Representation:** Приложение упаковано в Docker-контейнеры. Nginx раздает статику React и проксирует запросы к Node.js-приложению. База данных PostgreSQL запущена в отдельном контейнере.
- **More Information:** Реализует требование раздела 3.5 SRS.

## 4. Решения

### 4.1 Архитектурные решения (ADR)

**ID: ADR-001**
- **Title:** Выбор Node.js + Express для Backend
- **Context:** Необходимо создать быстрый REST API с высокой пропускной способностью для обработки множества одновременных запросов к базе репетиторов.
- **Options:** Python + Django, Java + Spring Boot, Node.js + Express.
- **Outcome:** Выбран Node.js + Express. Обоснование: асинхронная неблокирующая модель идеально подходит для I/O операций (запросы к БД), единый язык (JavaScript/TypeScript) с Frontend-частью.

**ID: ADR-002**
- **Title:** Выбор библиотеки для карт (Leaflet)
- **Context:** Требуется отображать местоположение репетиторов на карте без значительных финансовых затрат на этапе MVP.
- **Options:** Google Maps API, Mapbox, Leaflet + OpenStreetMap.
- **Outcome:** Выбран Leaflet + OpenStreetMap. Обоснование: полностью бесплатное решение с открытым исходным кодом, не требующее привязки банковской карты.

**ID: ADR-003**
- **Title:** Выбор JWT для аутентификации
- **Context:** Требуется разграничение прав (Ученик, Репетитор, Администратор) и защита API.
- **Options:** Сессии на основе cookie, JWT.
- **Outcome:** Выбран JWT. Обоснование: stateless-аутентификация идеально подходит для SPA (React), не требует хранения сессий на сервере.

**ID: ADR-004**
- **Title:** Архитектурное решение по добавлению чата
- **Context:** На втором раунде переговоров Заказчик потребовал внедрить встроенный чат для связи ученика и репетитора без сдвига дедлайнов.
- **Options:** Использовать готовое решение (Socket.io) или вынести чат в отдельный микросервис.
- **Outcome:** Выбрано решение Socket.io в рамках текущего Node.js-монолита с привлечением Junior-разработчика для параллельной верстки UI. Обоснование: позволяет уложиться в сроки без увеличения бюджета на полноценный микросервис.
